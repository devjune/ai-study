01

Why Koog? 공식적으로 내세우는 것

"Koog is a JVM (Java and Kotlin) framework for building predictable, fault-tolerant and enterprise-ready AI agents …" 예측 가능하고 장애를 견디고 기업 환경에서 쓸 수 있는 에이전트

기본 기능만 주는 프레임워크와 다른 점

  • 그래프 워크플로: 에이전트의 동작을 프롬프트에 맡기지 않고 데이터 클래스와 그래프로 적어 통제
  • 퍼시스턴스: 대화 메시지만이 아니라 실행 상태 전체를 체크포인트로 남김. 장애 복구와 되돌리기
  • 긴 대화를 줄이는 히스토리 압축, 조건을 건 재시도, 이력까지 옮기는 LLM 전환
  • 그래프, GOAP, LLM 플래너, 멀티 에이전트까지 한 프레임워크 안에서 조합

검증과 통합

  • JetBrains 제품과 사내 에이전트에 쓰이며, ML 엔지니어가 다듬은 프롬프트와 전략이 들어 있음
    어느 제품인지는 공식 자료가 밝히지 않음
  • Kotlin DSL과 Java API 둘 다 제공. 1.0부터 stable 모듈은 최소 1년간 깨지는 변경 없음
  • Spring Boot · Spring AI · Ktor 연동. 멀티플랫폼과 OpenTelemetry 지원
공식 GitHub 저장소 소개(인용문) · Why Koog · KotlinConf 2026 키노트 · Koog 1.0 · 예제: Banking · Chess · MCP · Langfuse

02 여섯 단계

1/6 기본 에이전트: AIAgent 하나로 시작

추가: AIAgent와 입력 루프 · 확인: REPL 응답 "5"

val agent = AIAgent(
    promptExecutor = promptExecutor,   // Spring AI 브리지가 만든 빈
    llmModel = KoogModels.QWEN3_4B_INSTRUCT,
    systemPrompt = "짧게 답한다.",
)
while (true) {
    print("❯ ")
    val line = readLine() ?: break
    println(agent.run(line))
}
$ koog step1
❯ 2 더하기 3은?
5

구성

  • AIAgent 하나로 에이전트 생성. 전략을 안 적으면 기본 전략으로 동작
  • PromptExecutor는 모델 호출을 맡는 Koog 인터페이스. Spring AI로 치면 ChatModel
  • 브리지는 Koog의 Spring AI 연동 스타터(koog-spring-ai-starter-model-chat). ChatModel을 LLMClient로 감싼 PromptExecutor 빈을 등록. Ollama 주소는 application.properties 그대로, 모델 이름은 코드의 LLModel이 매 호출 지정
  • 여기까지는 단일 호출. 다음 단계부터 도구, 스킬, 오케스트레이션, 메모리, 체크포인트를 차례로 추가
Harness07.kt · REPL: 한 줄씩 읽어 실행하고 출력을 반복하는 대화형 루프 (Read-Eval-Print Loop)

2/6 도구: 시그니처가 곧 스키마

추가: @Tool 캘린더 함수 · 확인: 도구 호출 왕복

class CalendarToolSet : ToolSet {
    private val entries = mutableMapOf("내일" to mutableListOf("10:00 팀 싱크", "14:00 디자인 리뷰"))
    @Tool
    @LLMDescription("날짜의 일정 목록을 돌려준다. 없으면 없음")
    fun schedules(@LLMDescription("날짜, 예: 내일") day: String): String {
        return entries[day]?.sorted()?.joinToString(", ") ?: "없음"
    }
    // add(day, time, title)는 같은 꼴. entries[day]에 넣는다
}
val calendar = CalendarToolSet()
toolRegistry = ToolRegistry { tools(calendar) }
❯ 내일 일정 알려줘
  dispatch    → assistant
  assistant   LLM #1 메시지 2개 → 도구 호출 schedules(day=내일)  1.0s
  assistant   schedules → 10:00 팀 싱크, 14:00 디자인 리뷰
  assistant   LLM #2 메시지 4개 → 답  1.1s
  assistant   완료 2.1s
내일은 10:00 팀 싱크, 14:00 디자인 리뷰가 있습니다.

여기서 알 수 있는 것

  • 도구는 원래 JSON 스키마로 모델에게 알려야 함. 여기서는 함수 시그니처와 설명 애노테이션이 그 스키마가 됨
  • 파라미터를 더하면 스키마도 따라 바뀜. 같은 꼴의 add(day, time, title)도 있어 데모에서 추가한 뒤 조회
  • 도구를 고르고, 부르고, 결과로 답을 만드는 왕복은 기본 전략이 처리

  • Koog 몫은 둘: 폴더에서 SKILL.md를 찾고, name·description 목록을 프롬프트 문자열로 만들어 줌(1.3.0-beta). 내 몫은 파일 읽기 도구를 쥐여 주는 것뿐

02 여섯 단계

4/6 오케스트레이션: 담당 에이전트 둘을 그래프로

추가: 조건 엣지 2줄 · 확인: 판교 사투리는 skill로, 나머지는 assistant로

fun dispatchRouter(
    askSkill: suspend (String) -> String,
    askAssistant: suspend (String) -> String,
) = strategy<String, String>("dispatch") {
    val skill by node<String, String>("skill") { askSkill(it) }
    val assistant by node<String, String>("assistant") { askAssistant(it) }
    edge(nodeStart forwardTo skill onCondition { "판교사투리" in it.replace(" ", "") })
    edge(nodeStart forwardTo assistant onCondition { true })
    edge(skill forwardTo nodeFinish)
    edge(assistant forwardTo nodeFinish)
}
dispatchRouter(
    askSkill = { skillAgent().run(withLastAnswer(it)) },
    askAssistant = { assistantAgent().run(it, "demo") },
)
❯ 판교 사투리 3으로 바꿔 줘: 내일 회식 오세요
  dispatch    → skill
❯ 내일 일정 알려줘
  dispatch    → assistant

엣지 규칙

  • 엣지는 선언한 순서대로 검사됨
  • 넓은 조건(onCondition { true })은 마지막에 둠. 앞에 오면 뒤 분기를 가림
  • if문과 다른 점: 노드와 엣지가 자료구조. 그림, 노드 이벤트, 체크포인트가 그 위에 붙음

5/6 챗 메모리: 세션 ID로 이어지는 대화

추가: ChatMemory 기능과 세션 ID · 확인: 앞 일정을 도구 호출 없이 답함

fun assistantAgent() = AIAgent(
    promptExecutor = promptExecutor,
    llmModel = KoogModels.QWEN3_4B_INSTRUCT,
    systemPrompt = "비서다. 짧게 답한다. " +
        "일정 질문에는 날짜마다 schedules 도구를 호출해야 한다. 예: '모레 일정은?' → schedules(day=모레). " +
        "도구 결과가 없음이면 없다고 답한다. 이력의 일정을 다른 날짜에 쓰지 않는다. 일정 추가에는 add 도구를 호출한다.",
    temperature = 0.0,
    toolRegistry = ToolRegistry { tools(calendar) },
) {
    install(ChatMemory) {
        chatHistoryProvider = historyProvider
    }
}
askAssistant = { assistantAgent().run(it, "demo") }
❯ 아까 말한 첫 번째 일정이 뭐였지?

여기서 알 수 있는 것

  • 실행 시작 때 세션의 이력을 읽고, 끝나면 이번 대화를 저장. run의 둘째 인자가 세션 ID, 다르면 이력도 분리
  • 이력은 에이전트가 아니라 ChatHistoryProvider가 보관. 요청마다 새로 만드는 에이전트도 같은 세션을 이어받음
  • 여기서는 브리지의 챗 메모리 스타터가 Spring AI ChatMemoryRepository를 감싼 provider 빈을 등록. 저장소는 Spring AI 것 그대로
