01

만든 이유와 사용 사례

"Koog is a JVM (Java and Kotlin) framework for building predictable, fault-tolerant and enterprise-ready AI agents" 예측 가능하고 장애를 견디며 기업 환경에 쓸 수 있는 에이전트

자기 문제에서 출발

  • JetBrains는 Junie(IDE 자율 코딩 에이전트)와 AI Assistant를 전부 Kotlin으로 개발
  • Koog는 그 내부 에이전트를 만들며 다듬은 방식을 프레임워크로 떼어 내 공개했다: "refined internal approaches and integrated them into a Kotlin framework"
  • 내부 제품이 Koog 자체를 쓰는지는 공개 자료로 확인되지 않는다. 내부 경험에서 나왔다는 데까지만 확인된다

공식 예제가 다루는 문제

  • Banking: 문의를 분류하고 도구를 부르는 업무 예제
  • Chess: 턴마다 반복되는 대국을 전략 그래프로 구성
  • GoogleMaps · Playwright · Unity: MCP로 외부 시스템 조작
  • OpenTelemetry · Langfuse · Weave: 운영 관측 연동

분류, 반복, 외부 연동, 관측 같은 운영 문제를 다룬 예제들이다.

03 STRATEGY GRAPH

왜 Strategy Graph인가

  • 갈리는 지점: 모델 접근층은 Spring AI에도 있다. Koog를 따로 고를 이유는 이 구역에 있다
  • 다른 기능의 토대: 도구 왕복, 히스토리 압축, 시각화가 전부 그래프의 노드와 구조로 동작한다(이번 검증에서 확인)
  • 다른 생태계도 같은 선택: LangGraph도 그래프 방식을 택했다. 여기서 익힌 개념은 프레임워크를 넘어 쓸 수 있다

구역 지도와 오늘 다룰 범위

오늘 노드·엣지 타입 조건 엣지 히스토리 공유 루프·상한 시각화
다음에 사전 정의 전략 병렬 노드 서브그래프 노드 간 데이터 전달 커스텀 노드
오늘 다섯 장(1/5~5/5) 이 구역의 나머지는 다음 기회에
공식 Why Koog: "explicit graphs built on verified domain models" · KotlinConf 2026 키노트: "deterministic state management" 실측 도구 왕복·압축·시각화가 그래프 위에서 동작(ToolsTest · ChatMemoryTest · asMermaidDiagram 출력)

03 STRATEGY GRAPH · 1/5

노드와 엣지: 타입이 붙은 자료구조

val draft  by nodeLLMRequest()
val polish by nodeLLMRequest()

edge(draft forwardTo polish)              // ✕
edge(draft forwardTo polish
    transformed { it.textContent() })    // ○
None of the following candidates is applicable:
fun <…, CompatibleOutput : OutgoingInput> edge(…)

타입 시그니처로 보는 것

  • nodeLLMRequest()의 타입은
    AIAgentNodeDelegate<String, Message.Assistant>. 입력은 문자열, 출력은 메시지다
  • 엣지는 나가는 쪽 출력이 들어가는 쪽 입력의 서브타입일 때만 성립한다. 거절 사유는 시그니처에 적혀 있다
  • Message.Assistant에 content가 없다. 응답이 파트 목록이라 textContent()를 거친다
연결 오류를 컴파일 시점에 받는다. 손으로 짰다면 실행해 봐야 알았다
진단 컴파일러 거절 메시지 원문 · 실측 StrategyGraphTest "두 노드를 잇는 커스텀 전략이 돈다"

03 STRATEGY GRAPH · 2/5

조건 엣지: 선언 순서대로 평가

val router = strategy<String, String>("route") {
    val classify by nodeLLMRequest()
    val math  by node("math")  { "수학 경로" }
    val other by node("other") { "일반 경로" }

    edge(nodeStart forwardTo classify)
    edge(classify forwardTo math  onTextMessage { "MATH" in it.text })
    edge(classify forwardTo other onTextMessage { true })
}

평가 규칙

  • 선언 순서대로 검사, 먼저 통과한 하나만 성립
  • { true }가 when의 마지막 가지 역할을 한다. 순서를 바꾸면 분기가 뒤집힌다
  • 분기 누락은 컴파일러가 잡지 않는다. when의 exhaustive 검사는 이 구조와 맞바꿨다

조건 세 종류

onCondition필터
onTextMessage필터 + String 변환
onToolCalls도구 호출 응답으로 한정
실측 StrategyGraphTest "조건 엣지가 분기를 고른다" · 4회 독립 실행 동일("수학 경로")

03 STRATEGY GRAPH · 3/5

프롬프트 히스토리: 노드들이 대화를 공유한다

val draft  by nodeLLMRequest()
val polish by nodeLLMRequest()

edge(nodeStart forwardTo draft)
edge(draft forwardTo polish transformed { "그 숫자에 10을 더하면?" })
edge(polish forwardTo nodeFinish transformed { it.textContent() })

run("2 더하기 3은?")   // → "15"

왜 15가 나오는가

  • polish가 받은 입력은 새 질문 한 줄뿐이다. 5라는 값을 넘긴 적이 없다
  • 그런데 모델이 "그 숫자"를 안다. nodeLLMRequest 노드들이 한 세션의 프롬프트 히스토리를 공유하기 때문이다
  • 노드 간 값 배선이 아니라 대화 누적 모델이다. 중간값을 손으로 나르지 않는다
  • 대가: 이력이 계속 자란다. 압축 노드(nodeLLMCompressHistory)가 존재하는 이유
실측 StrategyGraphTest 체인 출력 "15"(4회 동일) · 진단 바이트코드: 각 노드가 appendPrompt → requestLLM

03 STRATEGY GRAPH · 4/5

루프와 상한: 상한은 에이전트 설정에

val step by node("step") { "$it." }

edge(nodeStart forwardTo step)
edge(step forwardTo step       onCondition { it.length < 3 })
edge(step forwardTo nodeFinish onCondition { it.length >= 3 })

AIAgent(…, strategy = loop, maxIterations = 5)
run("")   // → "..."
// 탈출 조건을 { true }로 망가뜨리면, 무한루프 대신
AIAgentMaxNumberOfIterationsReachedException:
Agent couldn't finish in given number of steps (5).

상한의 위치

  • 자기 자신으로 가는 엣지가 곧 루프
  • 상한은 루프에 붙이지 않고 에이전트 설정에 적는다. 안 적으면 기본값이 들어간다
  • 즉 상한을 빠뜨릴 수 있는 자리가 없다
  • 대가: 상한은 루프별이 아니라 그래프 전체 걸음 수다. 노드를 늘리면 같은 값이 더 빨리 소진된다
실측 정상 루프는 셋째 바퀴 종료("...") · 진단 탈출 조건을 고의로 망가뜨려 받은 예외 원문

시각화: 전략이 스스로 그린다

자기 서술

  • asMermaidDiagram() 호출 한 번이면 전략의 다이어그램 텍스트가 나온다

정리

도입 시 얻는 것

  • 흐름이 타입 검사 대상인 자료구조가 됨
  • 루프 상한 누락이 구조적으로 불가능
  • 히스토리 압축 · 도구 스키마 · 원격 도구가 기본 제공
  • 기존 Spring AI 빈을 그대로 사용, 점진 도입 가능

고려할 점

  • 브리지·MCP 모듈은 beta 라인. 마이너 릴리스에서 API가 바뀔 수 있다
  • 브리지가 Spring BOM을 import, 버전 결정권이 넘어간다
  • 대화 저장소에 도구 호출 이력 미보존
