# Koog 세미나 발표 스크립트 (15분)

슬라이드 14장 기준. 괄호는 목표 시간, 꺾쇠는 행동. 따옴표 안은 그대로 말하면 되는 문장.
요령: 왼쪽 코드를 위에서 아래로 손가락으로 따라가며 읽고, 오른쪽 불릿은 읽지 말고 그중 한 문장만 힘줘 말한다.

터미널 1 = `koog step1` (7장에서 한 번, 12장에서 강제 종료 명령), 터미널 2 = `koog` (8장부터 끝까지 한 대화).
입력 문장과 실제 출력은 `데모 시나리오.md`.

---

## 1. 표지 (10초)

"JetBrains가 만든 JVM 에이전트 프레임워크, Koog를 소개합니다."

## 2. 목차 (15초)

"앞 2분 반은 Koog가 스스로 뭐라고 내세우는지 봅니다. 본론은 그 주장을 우리 Spring AI 스택에서 여섯 단계로 직접 확인하는 겁니다. 단계마다 코드를 보고 바로 돌립니다. 끝에 Spring AI와 뭐가 갈리는지 표로 정리합니다."

## 3. 소개 (40초)

〈왼쪽 등장 배경〉 "에이전트 프레임워크는 파이썬이 먼저였습니다. LangChain, LangGraph, CrewAI. JVM에는 2023년 LangChain4j가 나왔고, 2025년에 Kotlin 네이티브로 Koog가 나왔습니다."

〈연혁〉 "2025년 5월 공개, 2026년 5월 1.0. 1.0부터 stable 모듈은 최소 1년 동안 깨지는 변경이 없다고 보장합니다. 오늘 코드는 1.3.0입니다."

## 4. Why Koog? 공식적으로 내세우는 것 (60초)

〈인용〉 "공식 한 줄은 예측 가능하고, 장애를 견디고, 기업 환경에서 쓸 수 있는 에이전트입니다."

〈왼쪽〉 "Why Koog 문서가 '기본 부품만 주는 프레임워크와 갈리는 지점'으로 꼽는 게 이겁니다. 실행 논리를 명시적 그래프로 두는 그래프 워크플로. 상태 기계 전체를 체크포인트로 남겨 복구하고 되돌리는 내구 실행. 히스토리 압축, 재시도, 이력까지 옮겨 주는 LLM 전환. 그리고 그래프, GOAP, LLM 플래너, 멀티 에이전트까지 패턴 전부."

〈오른쪽〉 "JetBrains 제품과 내부 에이전트에서 쓴다고 하고, ML 엔지니어가 다듬은 프롬프트와 전략이 들어 있다고 합니다. 어느 제품인지는 공식 자료에 이름이 없습니다. Kotlin DSL과 Java API, Spring Boot와 Spring AI, Ktor 통합, 멀티플랫폼, OpenTelemetry."

"오늘은 이 중 그래프 워크플로, 내구 실행, 관측 셋을 직접 돌려 봅니다. 나머지는 마지막 표에서 출처만 남깁니다."

## 5. 기능 범위 (30초)

〈지도 전체를 쓸며〉 "공식 문서 목차의 주요 항목입니다. 넓습니다."

〈검은 칩들〉 "칠해진 여덟 개는 뒤에서 직접 돌려 봅니다. 나머지는 자료로 공유하고, 칩에 마우스를 올리면 한 줄 설명이 나옵니다."

## 6. Spring AI 위에 Koog, 여섯 단계로 (40초)

〈제목과 첫 불릿〉 "4장에서 Koog가 내세운 것 중 셋, 그래프 워크플로, 내구 실행, 관측을 우리 스택에서 직접 돌려 보는 게 목적입니다."

〈오른쪽 표, 위에서 아래로. 단계 이름만 읽음〉 "여섯 단계로 갑니다. 기본 에이전트, 도구, 스킬, 오케스트레이션, 챗 메모리, 내구 실행. 관측은 단계가 아니라 터미널에 계속 찍힙니다."

〈왼쪽 상자, 아래에서 위로〉 "배치는 이렇습니다. 맨 아래가 이미 쓰는 Spring AI, 모델과 대화 저장소입니다. 가운데 브리지가 그 빈들을 Koog 인터페이스로 포장해 주고, 맨 위에서 Koog의 전략 그래프 하나가 에이전트 둘을 지휘합니다."

〈둘째·셋째 불릿〉 "Spring AI를 재사용한 건 Koog의 전제가 아니라 우리 선택입니다. 그 위에 일정과 회사 말투를 아는 작은 비서를 만듭니다. 시작하겠습니다."

## 7. 1/6 기본 에이전트 (45초)

〈코드 위부터〉 "AIAgent 하나 만들고, 입력 루프를 돌립니다. 이게 전부입니다."

〈promptExecutor 줄〉 "봐 주실 건 이 promptExecutor입니다. 모델 호출을 맡는 Koog 인터페이스고, Spring AI로 치면 ChatModel 자리입니다. Koog가 배포하는 Spring AI 연동 스타터, 줄여서 브리지가 ChatModel을 감싸 이 빈을 등록해 줍니다. Ollama 주소는 쓰던 application.properties 그대로고, 모델 이름은 코드의 LLModel이 매 호출 넣습니다."

〈터미널 1: koog step1〉 "2 더하기 3은?" → 5.

"입력과 답뿐입니다. 아직 말만 할 줄 압니다. 이제 하나씩 붙입니다."

## 8. 2/6 도구 (50초)

"2단계는 도구입니다. 비서니까 일정부터 보게 하겠습니다."

〈코드 위부터〉 "평범한 Kotlin 함수입니다. 날짜를 받아 일정 문자열을 돌려줍니다. 한 일은 세 가지뿐입니다. 함수에 @Tool을 붙였고, 함수와 파라미터에 설명을 달았고, 이 함수를 ToolSet 클래스에 담아 〈아래 한 줄〉 레지스트리 한 줄로 넘겼습니다."

"도구를 모델에게 알리려면 원래는 JSON 스키마를 써야 합니다. 그런데 방금 스키마를 한 줄도 안 썼습니다. 함수 이름이 도구 이름이고, 파라미터가 스키마고, 애노테이션이 설명입니다. Spring AI의 @Tool과 같은 방식입니다."

〈터미널 2: koog〉 "내일 일정 알려줘" 〈출력 나오면, 흐린 줄을 위에서 아래로〉 "흐린 줄은 데모 코드가 Koog 이벤트 핸들러로 찍는 기록입니다. 첫 줄 dispatch는 요청을 담당에게 보낸 기록인데 4단계에서 봅니다. 그 아래가 지금 볼 것입니다. 첫 모델 호출의 결정이 '도구 호출 schedules(day=내일)'이고, 도구가 돌려준 값이 다음 줄, 그걸 실은 두 번째 호출의 결정이 '답'입니다. 걸린 시간도 붙어 있습니다. 이 왕복은 제가 짠 게 아니라 기본 전략이 합니다. 캘린더는 발표용 가짜입니다. 진짜 연동이면 return 안쪽만 바꾸면 됩니다."

## 9. 3/6 스킬 (50초)

"이번엔 능력을 파일로 꽂습니다."

〈frontmatter 위부터〉 "스킬은 frontmatter 달린 마크다운 파일 하나입니다. 이 name과 description의 목록이 에이전트가 들고 있는 스킬 카탈로그가 됩니다. '판교 사투리라고 말하면 이 스킬을 쓴다'까지 적혀 있습니다."

〈본문 강도〉 "본문에는 강도 1부터 11까지 지침이 있는데, 요청이 스킬에 해당할 때만 에이전트가 파일을 읽어 따릅니다. 프롬프트에 미리 싣지 않으니 토큰도 아낍니다."

"여기서 Koog가 해 주는 건 둘입니다. 폴더에서 SKILL.md를 찾아 주고, 그 name·description 목록을 프롬프트 문자열로 만들어 줍니다. 제가 한 건 에이전트에 파일 읽기 도구를 쥐여 준 것뿐입니다. Agent Skills는 Anthropic이 만들어 공개 표준으로 낸 형식이라 Koog 밖에서도 통합니다."

〈터미널 2〉 "판교 사투리 3으로 바꿔 줘: 내일 회식 오세요" 〈출력, 흐린 줄〉 "이번엔 스킬 에이전트로 갔고, 파일 읽기 도구로 SKILL.md를 통째로 읽은 뒤 모델을 다시 불렀습니다. 결과는 강도 3, 부드러운 사내 메모입니다."

〈여유 있으면〉 "끝까지 올리면 이렇게 됩니다." → "판교 사투리 11로 바꿔 줘: 내일 회식 오세요"

## 10. 4/6 오케스트레이션 (60초)

"여기서 문제가 하나 생깁니다. 2단계 캘린더 도구와 3단계 스킬을 한 에이전트에 다 주면, 이 4B 로컬 모델은 프롬프트로 아무리 일러도 엉뚱한 도구를 짚습니다. 그래서 담당을 나눴습니다. 캘린더만 가진 비서, 스킬만 가진 스킬 에이전트. 이제 요청을 담당에게 보내는 길이 필요합니다."

〈코드 위부터〉 "그 길이 이 전략입니다. 노드 둘이 각각 담당 에이전트를 부르고, 〈강조된 edge 두 줄〉 분기는 if문이 아니라 엣지 선언입니다. 판교 사투리가 들어 있으면 skill로, 나머지는 assistant로 갑니다. 에이전트 둘을 그래프 하나가 지휘합니다. 4장에서 멀티 에이전트 오케스트레이션이라고 부른 게 가장 작게는 이겁니다."

〈아래 호출부와 출력〉 "데모 코드에서는 여기에 실제 담당 에이전트를 꽂습니다. 스킬 쪽에는 직전 비서 답변을 바꿀 원문으로 붙여 넘겨서, 방금 들은 일정을 그대로 판교 사투리로 만들 수 있습니다. 터미널에서 보신 dispatch 줄이 이 전략의 노드에 들어간 기록입니다."

〈오른쪽 규칙〉 "규칙은 하나만 기억하시면 됩니다. 엣지는 선언한 순서대로 검사됩니다. 그래서 모두 받는 true 엣지는 반드시 마지막입니다. 분기를 빠뜨려도 컴파일러는 모릅니다. when과 다른 점입니다."

〈오른쪽 그림〉 "if문과 다른 점은 이 edge 줄이 실행문이 아니라 자료구조를 만든다는 겁니다. 그래서 asMermaidDiagram() 한 번에 이 그림이 나오고, 노드 단위로 이벤트가 잡히고, 다음다음 장의 체크포인트가 노드 단위로 붙습니다."

## 11. 5/6 챗 메모리 (45초)

"5단계는 챗 메모리입니다. 지금까지 비서는 요청마다 처음 보는 것처럼 답했습니다."

〈강조된 install 세 줄〉 "비서 에이전트에 ChatMemory 기능을 install로 붙였습니다. 정할 건 이력을 어디에 둘지, chatHistoryProvider 하나입니다. 여기서는 브리지의 챗 메모리 스타터가 Spring AI의 ChatMemoryRepository를 감싼 빈을 넣어 줍니다. 저장소는 Spring AI 것 그대로입니다."

〈아래 run 줄〉 "run의 둘째 인자가 세션 ID입니다. 실행 시작 때 이 세션의 이력을 읽고, 끝나면 이번 대화를 저장합니다. 이 에이전트는 요청마다 새로 만드는데도 대화가 이어집니다. 이력을 쥔 건 에이전트가 아니라 provider라서요."

〈터미널 2〉 "아까 말한 첫 번째 일정이 뭐였지?" 〈출력, 흐린 줄〉 "모델 호출 한 번에 메시지 4개, 그중 이력이 2개. 2단계의 질문과 답입니다. 도구 호출 없이 바로 답으로 끝났고, 0.6초입니다. 이력에서 꺼낸 겁니다."

## 12. 6/6 내구 실행 (50초)

"마지막은 4장에서 공식이 가장 세게 내세우는 것, 내구 실행입니다."

〈install 블록〉 "Persistence 기능을 붙이고 파일 저장소를 줬습니다. 이러면 노드가 끝날 때마다 체크포인트가 파일로 남습니다. 메시지 이력, 마지막 노드와 출력, 모델, 도구 목록. 정상 완료되면 완료 표시가 남습니다."

〈아래 블록〉 "저장 키가 run의 둘째 인자, runId입니다. 문서는 에이전트에 묶인다고 쓰는데 1.3.0 코드로는 이 값입니다. 챗 메모리의 세션 ID와 같은 값이라, 세션 하나가 대화 이력과 실행 상태를 함께 가집니다. 프로그램은 뜰 때 완료 표시 없는 체크포인트가 있으면 그 노드 다음부터 마저 돌립니다."

〈터미널 2〉 "내일 일정 알려 주고, 일정마다 준비할 것을 다섯 가지씩 이유와 함께 제안해 줘" 〈schedules 줄이 찍히면 터미널 1에서 미리 쳐 둔 pkill -9 Enter〉 "모델이 답을 만드는 도중에 프로세스를 죽였습니다."

〈터미널 2에서 koog 재시작〉 〈출력〉 "다시 뜨자마자 '중단된 실행 발견, nodeExecuteTool 다음부터'. 모델을 다시 부르지도, 도구를 다시 부르지도 않고 마지막 호출 하나로 답을 끝냈습니다. 되돌리기와 도구 부작용 롤백도 같은 기능입니다. 공식 문서에 있습니다."

〈라이브가 안 되면〉 슬라이드의 출력 블록을 가리키며 같은 말을 한다. 실측 캡처다.

## 13. Spring AI와 다른 점 (50초)

〈표 위에서 아래로, 흰 줄은 빠르게〉 "솔직하게 정리합니다. 모델 호출, 도구, 챗 메모리, 관측은 Spring AI에도 같은 역할로 있습니다." 〈칠해진 세 줄〉 "오늘 한 것 중 Spring AI 코어에 없는 건 셋입니다. 스킬 카탈로그(커뮤니티 spring-ai-agent-utils에는 있음), 노드와 엣지가 자료구조인 전략 그래프, 그리고 노드 단위 체크포인트로 복구하는 내구 실행."

〈마지막 줄〉 "압축 전략, 재시도 부품, 이력까지 옮기는 LLM 전환, 플래너는 오늘 안 돌려 봤습니다. 출처만 남깁니다."

"그러니까 Koog를 꺼내는 지점은 모델 호출이 아니라 그 바깥, 실행 논리를 그래프로 두고 그 상태를 남겨야 할 때입니다. 이게 공식 주장이고, 오늘 그 셋을 돌려 봤습니다."

- **LangChain4j와 차이는?** "그래프를 1급 자료구조로 두느냐가 갈림길입니다. 오늘 10장과 12장이 그 자리입니다."
- **모델을 바꾸면?** "접속은 application.properties, 모델 이름은 코드의 LLModel입니다. 브리지가 에이전트의 LLModel id를 매 호출 ChatOptions로 넘겨 프로퍼티의 모델 이름을 덮습니다. 그래서 둘 다 바꿔야 합니다."
- **분기 누락은 어떻게 막나?** "true 받침 엣지를 관례로 두는 수밖에 없습니다. when 같은 전수 검사는 없습니다."
- **체크포인트 키가 왜 세션인가?** "Persistence는 runId로 저장하고 찾는데, run의 둘째 인자가 그 runId입니다. 공식 문서는 '에이전트에 묶인다'고 쓰는데, 코드로는 run 단위입니다. 에이전트 id만 주고 둘째 인자를 비우면 실행마다 새 키라 복구가 안 됩니다."
- **재시작 뒤 챗 메모리는?** "오늘 저장소가 인메모리라 재시작하면 대화 이력은 비고, 체크포인트만 파일에 남습니다. JDBC 저장소로 바꾸면 둘 다 남습니다."
- **비서한테 "뭐 할 수 있어?"라고 물으면?** "비서는 스킬 목록을 모릅니다. 담당을 나눈 대가입니다. 카탈로그를 비서 프롬프트에 넣어 봤는데 4B의 말투가 실행마다 흔들려서 뺐습니다. 스킬 이름을 대면 스킬 에이전트가 파일을 읽고 설명합니다. '판교사투리란?'처럼요."
- **흐린 줄은 뭔가?** "Koog의 EventHandler 기능입니다. 노드 진입, 모델 호출 완료(도구 호출인지 답인지, 걸린 시간), 도구 결과, 에이전트 완료 이벤트에 콜백을 걸어 한 줄씩 찍습니다. 에이전트마다 install 한 줄, 출력 형식은 Trace.kt 한 파일입니다."
- **전략 그림은 어디까지 나오나?** "asMermaidDiagram()이 Mermaid 텍스트를 돌려줍니다. 노드와 엣지는 나오지만 조건식 내용은 안 나오고 onCondition이라고만 적힙니다."
- **calls 리스트는 뭔가?** "모델의 도구 호출을 검증하는 테스트용 기록입니다. LLM 응답은 흔들려도 도구 호출 여부는 단정할 수 있어서요."
- **tool과 tools 차이는?** "tools는 @Tool 함수를 품은 클래스를 통째로 스캔하고, tool은 완성된 Tool 객체 하나를 넣습니다."

## 준비 체크리스트

- 모델 웜업 + 2시간 고정 (발표 직전 1회):
  `curl -s localhost:11434/api/chat -d '{"model":"qwen3:4b-instruct","messages":[{"role":"user","content":"안녕"}],"stream":false,"keep_alive":"2h"}' -o /dev/null`
- 체크포인트 폴더 비우기: `rm -rf /tmp/koog-checkpoints` (리허설의 미완료 실행이 남아 있으면 기동 때 자동 재개됨)
- 터미널 두 개를 미리 띄워 웜업 질문 한 번씩: 터미널 1 `koog step1`, 터미널 2 `koog`
  (명령 설치 위치는 /opt/homebrew/bin/koog. 내부에서 bootJar 후 jar 실행)
- 터미널 1에 12장용 강제 종료 명령을 미리 쳐 두기(Enter만 남김): `pkill -9 -f 'profiles.active=harness'`
- 데모 입력을 복사해 둘 것. 장별 입력과 실측 출력, 즉흥 입력 후보, 어긋날 때 대처는 `데모 시나리오.md`
- 슬라이드는 file://로 열고 #1 확인 (키보드 →로 진행)
