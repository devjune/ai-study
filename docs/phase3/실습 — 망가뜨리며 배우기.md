## 실험 1 — 타입이 연결을 거절한다 (5분)

**파일** `demo-phase3/src/test/kotlin/com/example/phase3/StrategyGraphTest.kt` **27행**

```kotlin
edge(draft forwardTo polish transformed { "그 숫자에 10을 더하면?" })
```

`transformed { ... }` 부분을 지워 이렇게 만듭니다.

```kotlin
edge(draft forwardTo polish)
```

```bash
./gradlew test --tests StrategyGraphTest
```

**예상** — 테스트가 실패하는 게 아니라 **컴파일이 안 됩니다.** 거절 메시지에 이 줄이 있는지 보세요.

```
CompatibleOutput : OutgoingInput
```

**무엇을 느끼는가** — `nodeLLMRequest()`의 출력은 `String`이 아니라 `Message.Assistant`입니다. 나가는 쪽 출력이 들어가는 쪽 입력의 서브타입일 때만 엣지가 붙고, 그 규칙이 `edge` 시그니처에 박혀 있습니다. **손으로 짰다면 실행해야 알았을 연결 오류를 컴파일 단계에서 받습니다.**

> 한 걸음 더 — `transformed { it.content }`로 바꿔 보세요. 역시 거절당합니다. `Message.Assistant`에는 `content`가 없고 `parts` 목록이라 `textContent()`를 거쳐야 합니다. 이 구조가 실험 5에서 다시 나옵니다.

**되돌리기** 27행을 원래대로.

## 실험 2 — 선언 순서가 분기를 지배한다 (5분)

**같은 파일 99~100행** (하단의 `assistantRouter()` 안)

```kotlin
edge(nodeStart forwardTo schedule onCondition { "일정" in it })
edge(nodeStart forwardTo answer onCondition { true })
```

두 줄의 **순서만** 바꿉니다.

```kotlin
edge(nodeStart forwardTo answer onCondition { true })
edge(nodeStart forwardTo schedule onCondition { "일정" in it })
```

```bash
./gradlew test --tests StrategyGraphTest
```

**예상** — 컴파일은 통과하고 **테스트가 실패합니다.**

```
expected:<"10:00 팀 싱크, 14:00 디자인 리뷰"> but was:<모델이 그냥 답한 문장>
```

**무엇을 느끼는가** — 엣지는 선언한 순서대로 검사되고 먼저 통과한 하나만 성립합니다. `{ true }`가 위로 올라가면 뒤의 조건은 영원히 평가되지 않습니다. **`when`의 가지 순서와 같은 규칙인데, 적히는 자리가 서비스 코드가 아니라 그래프 정의 안입니다.**

여기서 같이 생각해 볼 것: 이 실수를 컴파일러는 못 잡습니다. 실험 4에서 다시 만납니다.

**되돌리기** 두 줄 순서 복구.

## 실험 3 — 무한루프 대신 예외 (5분)

**같은 파일 82행**

```kotlin
edge(step forwardTo step onCondition { it.length < 3 })
```

탈출 조건을 없앱니다.

```kotlin
edge(step forwardTo step onCondition { true })
```

```bash
./gradlew test --tests StrategyGraphTest
```

**예상** — 멈추지 않고 도는 게 아니라 몇 초 만에 끊깁니다.

```
AIAgentMaxNumberOfIterationsReachedException:
Agent couldn't finish in given number of steps (5).
```

**무엇을 느끼는가** — 89행의 `maxIterations = 5`가 받아 낸 것입니다. 중요한 건 **그 값을 적는 자리**입니다. 루프 안이 아니라 에이전트 설정이고, 안 적으면 기본값이 들어갑니다. 즉 **상한을 빠뜨릴 수 있는 자리가 구조적으로 없습니다.**

대가도 같이 보세요. 이 상한은 루프별이 아니라 **그래프 전체의 걸음 수**입니다. 노드를 늘리면 같은 값이 더 빨리 소진됩니다. `maxIterations`를 `2`로 바꿔 돌려 보면 정상 루프도 끊기는 걸 볼 수 있습니다.

**되돌리기** 82행 복구 (`maxIterations`도 건드렸다면 5로).

## 실험 4 — 분기 하나 추가하기 · 핵심 (15분)

여기가 이 실습의 중심입니다. **같은 일을 양쪽에서 해 보고, 컴파일러가 무엇을 잡아 주는지 비교합니다.**

### 4-A. Koog 쪽 (7분)

**라우팅 전략(하단 `assistantRouter()`, 95~103행)**에 "점심 추천" 분기를 하나 더 만듭니다.

노드 선언 옆(97행 근처)에 한 줄:

```kotlin
val lunch by node<String, String>("lunch") { "오늘은 구내식당 B코너" }
```

엣지 두 줄 추가. **`{ true }` 엣지보다 반드시 위에** 둡니다 (실험 2에서 배운 것):

```kotlin
edge(nodeStart forwardTo lunch onCondition { "점심" in it })
edge(lunch forwardTo nodeFinish)
```

마지막으로 입력과 기대값을 바꿔 확인합니다.

```kotlin
val result = agent.run("오늘 점심 뭐 먹을까")
result shouldBe "오늘은 구내식당 B코너"
```

```bash
./gradlew test --tests StrategyGraphTest
```

**세어 볼 것** — 기존 줄 중 **고친 것**과 **새로 더한 것**이 각각 몇 줄인가.

### 4-B. phase2 쪽 — 읽기만 (5분)

같은 일을 손조립으로 하면 어디를 건드려야 하는지 **코드를 열어서 눈으로만** 확인합니다. (고치지 않습니다)

**`demo-phase2/src/main/kotlin/com/example/demo/pattern/ch02/Routing.kt`**

| 줄 | 무엇 |
|---|---|
| 99 | `enum class Route { ORDER, POLICY, GENERAL }` — 값 추가 |
| 66 | `when (decision.route())` — 가지 추가 |
| 82~88 | `CLASSIFIER` 프롬프트 — 분류 설명 추가 |
| 14~37 | 화면에 보여 주는 코드 문자열 — 일관성 맞추려면 여기도 |

### 4-C. 비교하고 적기 (3분)

그리고 **다음 질문에 스스로 답해 보세요. 여기서 나오는 답이 발표의 알맹이가 됩니다.**

1. 어느 쪽이 손댈 자리가 적었는가?
2. **양쪽에서 분기 하나를 빠뜨렸다면, 컴파일러가 잡아 주는 쪽은 어디인가?**
3. 그래서 둘 중 어느 쪽이 "좋다"고 말할 수 있는가?

> 2번이 핵심입니다. phase2의 `when`은 enum에 값이 늘면 **빠진 가지를 컴파일러가 지적합니다.** Koog의 엣지는 그런 검사가 없습니다 — 분기를 빠뜨려도 컴파일은 통과하고, 기본 엣지가 없으면 런타임에 막힙니다.
>
> 즉 이건 "Koog가 이긴다"가 아니라 **거래**입니다. 흐름이 값이 되는 대신, 분기 누락에 대한 컴파일 보장을 잃습니다. 실험 1에서 얻은 보장(연결 타입)과 실험 4에서 잃은 보장(분기 누락)이 서로 다른 층위라는 것 — 이게 시니어 청중에게 가장 정직하고 설득력 있는 지점입니다.

**되돌리기** `git checkout demo-phase3/src/test/kotlin/com/example/phase3/StrategyGraphTest.kt`

## 실험 5 — 스키마를 안 쓴다는 것 (5분)

**`ToolsTest.kt` 103행의 도구 함수**

```kotlin
fun exchangeRate(@LLMDescription("통화 코드, 예: USD") code: String): String {
```

파라미터를 하나 더 답니다.

```kotlin
fun exchangeRate(
    @LLMDescription("통화 코드, 예: USD") code: String,
    @LLMDescription("소수점 자리 수") digits: Int,
): String {
```

(본문 `when` 블록은 그대로 둬도 컴파일됩니다. `digits`를 안 써도 경고만 납니다.)

```bash
./gradlew test --tests ToolsTest
```

**예상** — 4건 중 **스키마 테스트 1건만** 실패하면서, 바뀐 서술자를 보여 줍니다.

```
Unexpected elements from index 1 expected:<["code"]> but was:<["code", "digits"]>
```

**무엇을 느끼는가** — **JSON 스키마를 한 줄도 쓰지 않았는데** 파라미터 추가가 도구 서술자에 그대로 반영됐습니다. 손조립이라면 함수 시그니처와 스키마 문서를 따로 맞춰야 하고, 둘이 어긋나도 아무도 안 알려 줍니다. 여기서는 시그니처가 곧 스키마입니다.

> **여기서 꼭 보고 넘어갈 것** — 나머지 두 테스트는 **그대로 통과합니다.** 도구를 실제로 부르는 테스트들인데, 인자가 하나 늘었는데도 모델이 `digits`까지 채워서 호출했다는 뜻입니다. 바뀐 시그니처가 서술자를 거쳐 **프롬프트까지 자동으로 전달됐다**는 증거입니다. 실습 다섯 개 중 "좋은 점"이 가장 직접 보이는 자리입니다.

**되돌리기** `git checkout demo-phase3/src/test/kotlin/com/example/phase3/ToolsTest.kt`
