## 실험 1 — 선언 순서가 분기를 지배한다 (5분)

**파일** `demo-phase3/src/main/kotlin/com/example/phase3/DispatchRouter.kt` **17~18행**

```kotlin
edge(nodeStart forwardTo skill onCondition { "판교 사투리" in it })
edge(nodeStart forwardTo assistant onCondition { true })
```

두 줄의 **순서만** 바꿉니다.

```kotlin
edge(nodeStart forwardTo assistant onCondition { true })
edge(nodeStart forwardTo skill onCondition { "판교 사투리" in it })
```

```bash
./gradlew test --tests StrategyGraphTest
```

**예상** — 컴파일은 통과하고 스킬 라우팅 테스트가 실패합니다. 라우팅 테스트는 LLM 없이 도니까 결과가 매번 같습니다.

```
expected:<"skill: 판교 사투리 3으로 …"> but was:<"assistant: 판교 사투리 3으로 …">
```

**무엇을 느끼는가** — 엣지는 선언한 순서대로 검사되고 먼저 통과한 하나만 성립합니다. `{ true }`가 위로 올라가면 뒤의 조건은 영원히 평가되지 않습니다. **`when`의 가지 순서와 같은 규칙인데, 적히는 자리가 서비스 코드가 아니라 그래프 정의 안입니다.**

여기서 같이 생각해 볼 것: 이 실수를 컴파일러는 못 잡습니다. 실험 2에서 다시 만납니다.

**되돌리기** 두 줄 순서 복구.

## 실험 2 — 분기 하나 추가하기 (10분)

**같은 파일**에 "점심 추천" 분기를 하나 더 만듭니다.

노드 선언 옆(15행 아래)에 한 줄:

```kotlin
val lunch by node<String, String>("lunch") { "오늘은 구내식당 B코너" }
```

엣지 두 줄 추가. **`{ true }` 엣지(18행)보다 반드시 위에** 둡니다 (실험 1에서 배운 것):

```kotlin
edge(nodeStart forwardTo lunch onCondition { "점심" in it })
edge(lunch forwardTo nodeFinish)
```

`StrategyGraphTest.kt`에 테스트를 하나 더해 확인합니다.

```kotlin
test("점심 질문은 점심 추천으로 간다") {
    router().run("오늘 점심 뭐 먹을까") shouldBe "오늘은 구내식당 B코너"
}
```

**세어 볼 것** — 기존 줄 중 고친 것과 새로 더한 것이 각각 몇 줄인가. 그리고 **분기 하나를 빠뜨렸다면 컴파일러가 잡아 줬을까?**

> 핵심은 이겁니다. `when`은 enum 가지가 빠지면 컴파일러가 지적하지만, 그래프의 엣지는 그런 검사가 없습니다. 흐름이 값이 되는 대신 분기 누락의 컴파일 보장을 잃는 **거래**입니다.

**되돌리기** `git checkout demo-phase3/src/`

## 실험 3 — 스키마를 안 쓴다는 것 (5분)

**`ToolsTest.kt` 71행의 도구 함수**

```kotlin
fun exchangeRate(@LLMDescription("통화 코드, 예: USD") code: String): String {
```

파라미터를 하나 더 답니다.

```kotlin
fun exchangeRate(
    @LLMDescription("통화 코드, 예: USD") code: String,
    @LLMDescription("소수점 자리 수") digits: Int,
): String {
```

(본문 `when` 블록은 그대로 둬도 컴파일됩니다. `digits`를 안 써도 경고만 납니다.)

```bash
./gradlew test --tests ToolsTest
```

**예상** — 4건 중 **스키마 테스트 1건만** 실패하면서, 바뀐 서술자를 보여 줍니다.

```
Unexpected elements from index 1 expected:<["code"]> but was:<["code", "digits"]>
```

**무엇을 느끼는가** — **JSON 스키마를 한 줄도 쓰지 않았는데** 파라미터 추가가 도구 서술자에 그대로 반영됐습니다. 손조립이라면 함수 시그니처와 스키마 문서를 따로 맞춰야 하고, 둘이 어긋나도 아무도 안 알려 줍니다. 여기서는 시그니처가 곧 스키마입니다.

> **여기서 꼭 보고 넘어갈 것** — 나머지 테스트는 **그대로 통과합니다.** 도구를 실제로 부르는 테스트들인데, 인자가 하나 늘었는데도 모델이 `digits`까지 채워서 호출했다는 뜻입니다. 바뀐 시그니처가 서술자를 거쳐 **프롬프트까지 자동으로 전달됐다**는 증거입니다.

**되돌리기** `git checkout demo-phase3/src/test/kotlin/com/example/phase3/ToolsTest.kt`
